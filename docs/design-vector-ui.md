# HWRun OS 上层显示设计稿（矢量场景图 + TUI 双模）

版本：0.1（草案，待评审）
状态：设计讨论稿——本文件为独立草案，待定稿后并入 `docs/design.md` 正文。
关联：`HWRun OS DISPLA.txt`（DISPLAY 协议设计）、`HWRun OS 上层应用插件.txt`（UI/SHELL/CONSOLE/DESKTOP）、`docs/design.md` §6 用户态插件链。
原则：**本体（OS 容器）保持轻量：机制与策略分离，显示只做"合成器 + 图元命令"，不做像素业务；TUI 与矢量 GUI 共享一套协议底座，按可用性渐进启用。**

---

## 1. 动机与定位

### 1.1 想解决的问题

1. 本体轻量：不希望 UI 层在 OS 侧携带庞大位图/纹理资产与逐像素业务逻辑。
2. 常规 UI 效果：期望窗口、圆角、文本、缩放、动画、网格画布等达到主流桌面观感，而非退回纯字符终端。
3. 隔离与安全：应用/上层插件不直接碰帧缓冲，避免污染与越权。
4. DPI/分辨率无关：高分屏与多尺寸输出下图形不糊。

### 1.2 路线判断

采用 **"命令级矢量 + 单点合成"**（display-list / scene-graph 模型），而不是"位图纹理整帧搬运"：

- 上层只提交**图元命令列表**（矩形/圆角/文本/路径/图像引用/变换）；
- OS 本体持有一个**矢量光栅器**，将场景图合成为帧；无 GPU 时软光栅到 dumb buffer，有 GPU 时可换后端；
- 网络/进程边界传输的是命令（几十字节）而非帧（数 MB），本体带宽与内存开销随场景复杂度而非分辨率增长。

> 参照：RDP 早期 GDI 命令流、浏览器 compositor、Qt Scene Graph、Vello/tiny-skia 等"场景图 + 单合成"架构，均验证"命令比像素省"这一前提。

## 2. 分层架构

```
上层应用插件 (SANDBOX/UI 应用/DESKTOP/CONSOLE/TERMINAL 各 .so)
   │  只发"图元命令 + 事件订阅"（UI 协议 / 或直连 renderer 内部 API）
   ▼
UI 合成层（唯一合成器，用户态 .so，持有场景图、damage 跟踪、动画时钟）
   │  光栅化：path 填充/文本/图像采样 → 合成帧
   ▼
矢量光栅器（本体内置；软渲 CPU 或 GPU 后端可选）
   ▼
DISPLAY 协议（沿用既有设计：DRM/KMS 与 FBDEV 双后端）→ dumb buffer / PageFlip
```

要点：

1. **DISPLAY 保持帧输出抽象不变**（与 `HWRun OS DISPLA.txt` 一致），矢量化不侵入 DRM/KMS 层；它照旧收"帧"，只是帧的来源从"业务插件直接画"变为"合成器光栅化输出"。
2. **UI 协议定义在图元层**（本设计稿的核心增量）：协议内容 = 场景树的增删改、图元参数、输入事件、动画时间戳。UI 插件与渲染器之间不存在像素协议。
3. **TUI 与 GUI 共享底座**：TUI 是图元协议的一个"文本网格"子集（cell 命令），可走同一合成路径（字形光栅化），也可保留现有字符直写路径。二者不互斥：**文本语义层统一，呈现层（网格/自由布局）分离**。

## 3. 核心概念

### 3.1 图元基元集（v1 最小集）

| 基元 | 语义 | 参数要点 |
|---|---|---|
| `rect` | 实心/描边矩形 | x,y,w,h,radius(圆角),fill,stroke |
| `path` | 通用矢量路径 | 子路径段(直线/三次曲线/弧), 填充规则 |
| `text` | 文本跨度 | 字符串、字体、字号、颜色、行高、布局模式(grid/free) |
| `image` | 图像引用 | 资源 id（位图仅作图标/照片内容，非 UI 主路） |
| `gradient` | 线性/径向渐变（合成期栅格化） | 端点、色标、空间 |
| `transform` | 嵌套变换（2D 仿射，预留 3D） | 平移/缩放/旋转/矩阵 |
| `clip` | 裁剪 | 与基元组合成子树 |
| `layer` | 离屏图层（模糊/半透明/特效合成用，可选慢路径） | 尺寸、滤镜 |

设计约束：**v1 不要求 GPU**——全部基元可由 CPU 光栅器完成；`gradient/layer` 是唯一引入像素合成语义的基元，默认关闭（无特效模式），需效果时按 damage 局部启用。

### 3.2 场景树与显示列表

- 合成器维护一棵**保留式场景树**（retained），上层提交命令为"树的局部 patch"，而非整帧重绘。
- 每帧仅重光栅 **damage 区域**（脏矩形集合），与 DISPLAY 的 PageFlip 对应：CPU 软渲时只刷新受损行。
- 场景树节点引用图元 + transform + 可见性 + 输入命中区域；**命中测试走场景树**（矢量命中，天然支持任意形状按钮）。

### 3.3 文本

- 语义层：`text` 携带统一文本对象（UTF-8），布局交给合成器；TUI 模式下布局退化为 cell 网格。
- 字形：本体内置一款可变/基础矢量字体集（如 Noto Sans 子集或内嵌 bitmap fallback）；复杂排版（RTL/复杂文种/高级断行）标为可选（harfbuzz 类依赖做成可选 .so，不内建于本体）。
- 文本与路径一致走矢量光栅：缩放不糊。

## 4. 矢量渲染器选型

| 方案 | 形态 | 优点 | 代价 | 判定 |
|---|---|---|---|---|
| 自研最小光栅器 | C，path→tessellation→span fill + 字体字形采样 | 零外部依赖、体积小、契合"本体轻量" | 曲线/AA/文本质量与工期风险 | **首选路线**（v1 覆盖 rect/path/text 即可） |
| tiny-skia / Skia | C++/Rust 静态库 | 质量成熟、效果全 | 体积大、C++/Rust 工具链入本体 | 备选（若自研质量不可接受时） |
| Vello | Rust、GPU 优先 | 极高质量曲线/合成 | 依赖 GPU/复杂、与 C 本体集成重 | 远期 GPU 路线备选 |
| Cairo | C 老牌 | C 可链、稳定 | 体积/性能一般，文本与合成弱 | 不优先 |

> 建议：本体内置自研**子集光栅器**（rect/path/text/AA/damage，目标 ≤3k 行 C），上层效果层再接可选增强（渐变/模糊）——保持"机制轻量、效果按需"。

## 5. 协议草案（图元命令，示意）

```
ui.begin_frame(seq)
ui.patch(scene_id, {upsert: [node...], remove: [...]})
   node := {id, parent, kind: rect|path|text|image|transform|clip|layer, props}
ui.commit(seq, {damage_hint})
ui.bind_input(scene_id, {hit_map...})        // 命中树
event → ui (input): {type: pointer|key|wheel|zoom, at: {x,y}, ...}
```

- 传输层：本地插件经 METAPROTO（既有总线）调用合成器 .so；跨进程/网络场景可将命令序列化后复用 NP/FS_TRANSFER 通道——协议与传输解耦。
- 认证：命令粒度鉴权（某 scene 能否提交/能否用 layer 特效），对应现有 SP 策略面。

## 6. 与既有设计的一致性

- DISPLAY 帧输出（DRM/KMS/FBDEV）**不改**，见 `HWRun OS DISPLA.txt` §1.3。
- UI 协议仍为上层插件协议（`上层应用插件.txt` UI 部分），本稿将其语义从"渲染表面/直接绘制"细化为"场景图命令"。
- 上层插件（SANDBOX/UI/SHELL/CONSOLE/DESKTOP/PKGMGR/MONITOR）当前"仅设计未实现"（见 `docs/txt_inventory.md`），本稿不改变其模块划分，仅约束其与 DISPLAY 之间的渲染契约。
- 设计稿中的"TUI 优先"与"字符/图形渲染"（`上层应用插件.txt` 原则）被保留为**双模中的 TUI 模**。

## 7. 落地方案（分期，上层不急故优先级低）

1. **P1 概念验证（宿主 Linux）**：自研子集光栅器（rect/path/text + AA + damage）输出 x11/Wayland 窗口或 QEMU dumb buffer，验证观感与性能。
2. **P2 合成器 .so + UI 协议**：场景树 patch、命中、事件回传，接入 METAPROTO；TUI 文本网格作为 text 基元子集同时打通。
3. **P3 DISPLAY 接入**：合成器输出接 DISPLAY 插件的 dumb buffer/PageFlip（QEMU 环境先验证）。
4. **P4 上层应用**：CONSOLE/TERMINAL→DESKTOP/窗口管理器→应用图标、缩放网格画布类应用。
5. 验收：本体二进制/内存增量受控（渲染器 + 合成器预估 ≤ 数百 KB）；TUI 在无图形能力环境仍是第一可用路径；矢量应用在任意缩放无马赛克。

## 8. 待决问题

1. 渲染器自研 vs 接库的最终取舍（以 P1 原型质量为判据）。
2. 文本布局深度：v1 覆盖基础 LTR + 单字重，还是直接带 harfbuzz 可选依赖。
3. 动效/合成特效（模糊、渐变、透明层）是否进 v1，还是全部走 `layer` 慢路径后置。
4. 事件回传细节：多输入设备、焦点、IMM（输入法）坐标空间。
5. 画布类应用需求（无限缩放 + 多级网格线分层配色）作为矢量管线的**首个验收样例**：网格是典型无限细节矢量用例，天然检验 AA/损伤区/坐标精度，纳入 P2 验收。
6. 颜色/主题规范（本体默认与终端配色一致性），待 UI 工程化时定稿。
